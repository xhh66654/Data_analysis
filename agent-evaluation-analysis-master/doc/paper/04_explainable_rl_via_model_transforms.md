# Explainable Reinforcement Learning via Model Transforms

对应 PDF：`NeurIPS-2022-explainable-reinforcement-learning-via-model-transforms-Paper-Conference.pdf`

## 一、内容介绍

这篇论文讨论的是：**当强化学习智能体的行为和人类观察者预期不一致时，怎样自动生成解释？**

作者提出的核心思路很有意思：不一定非要去直接解释神经网络内部参数，也不一定必须完全知道环境模型。即便我们只有一个**部分已知的环境模型**，仍然可以通过对这个模型施加一系列**形式化变换（model transforms）**，找到“为什么观察者会误解智能体行为”的原因。

论文把这个问题形式化为 **RLPE（Reinforcement Learning Policy Explanation）**。在这个设定中有三方：

- **actor**：真实执行策略的强化学习智能体；
- **observer**：对智能体行为有自己预期的人；
- **explainer**：掌握一部分环境模型，并尝试生成解释的系统。

解释的目标是：找到一组模型变换，使得智能体在“变换后的模型”中的行为，能够和观察者原本期待的行为对齐。只要找到了这组变换，就说明观察者与智能体之间的“理解落差”大概率来自这些模型要素。

## 二、论文主线

这篇论文的核心逻辑是：

1. 人类之所以觉得 RL 智能体“行为奇怪”，通常是因为人和智能体对环境约束或动态的理解不一致；
2. 这种不一致可以表示成一种**anticipation gap（预期差）**；
3. 如果通过修改环境模型中的某些部分，能让智能体行为与观察者预期一致，那么这些被修改的部分就可以构成解释；
4. 因此，“解释”可以被视为一个**搜索合适模型变换序列**的问题。

## 三、方法讲解

### 1. 什么叫“模型变换”

论文把 transform 定义得比较宽泛：只要是把一个 MDP 映射成另一个 MDP 的操作，都算 transform。

常见例子包括：

- 忽略某些状态特征；
- 改写动作空间；
- 忽略环境的随机性，把随机转移近似成确定转移；
- 放松或去掉某些约束；
- 修改动作的前提条件或效果。

这些变换原本常用于**加速规划和学习**，作者把它们挪用到“解释”任务上。

### 2. RLPE 的关键思想

假设观察者期待智能体在某些状态下采取策略 A，但真实智能体采取的是策略 B。  
解释器的任务不是直接说“网络为什么这么想”，而是去试：

- 如果忽略燃油约束会怎样？
- 如果去掉某个前提条件会怎样？
- 如果把环境当成确定性的会怎样？

当某个变换施加后，智能体策略变得和观察者预期一致，就说明观察者可能忽略了该约束、该风险或该环境性质。

### 3. 一个很典型的例子

论文用出租车场景举例：  
观察者以为出租车应该直接去接乘客，但真实智能体先去加油站。为什么？

如果解释器施加“移除燃油约束”这个变换后，智能体就会直接去接乘客，那么解释就成立了：  
**观察者之所以不理解，是因为没有把燃油约束纳入自己的环境模型。**

这个例子很能说明论文方法的魅力：解释不是从黑盒网络里硬抠出来的，而是通过比较“原模型”和“变换后模型”的差异来给出。

## 四、关键知识点讲解

### 1. 解释的对象是“预期差”

这篇论文特别值得记住的一点是：  
它不是单纯解释“策略是什么”，而是解释“**为什么真实策略和人的预期策略不一致**”。

所以它本质上是一种面向人机协作的解释框架。

### 2. 部分模型也有解释价值

论文强调，即使转移概率和奖励函数不完全已知，只要状态空间、动作空间或部分结构是已知的，模型仍然可以被利用来解释行为。

这说明：

- 解释不一定要求完整精确模型；
- 哪怕是模型自由 RL，也可以借助外部模型做解释。

### 3. 符号级变换比纯特征可视化更自然

因为 transform 操作的是 MDP 中有明确语义的元素，比如：

- 某个状态变量；
- 某个动作的前提条件；
- 某个环境约束；
- 某种随机性来源。

所以这些解释往往更容易被翻译成自然语言，而不是只给出一张难以理解的热力图。

### 4. 状态变换与动作变换

论文明确区分了两类变换：

- **状态空间变换**：例如忽略部分状态特征，把若干状态合并；
- **动作空间变换**：例如简化动作、去掉某些动作效果、做确定化处理。

这个区分很重要，因为很多“误解”可能来自不同层面：

- 有时是观察者少看了某个状态约束；
- 有时是观察者误以为某个动作没有副作用；
- 有时是观察者忽略了环境随机性。

## 五、论文贡献如何理解

作者的主要贡献可以概括为三点：

1. 提出把 **MDP transform** 用于 RL 行为解释；
2. 正式定义 RLPE 问题；
3. 在单智能体和合作多智能体基准上验证这种思路有效。

这篇论文的创新不在于“更好地训练策略”，而在于提出了一种**结构化、可搜索、可对齐人类预期**的解释方式。

## 六、可作为复习的重点

- RLPE 三方：actor、observer、explainer；
- 解释目标：缩小 anticipated policy 与 actual policy 的差距；
- transform 的含义：对 MDP 进行有语义的结构变换；
- 解释机制：找到能让真实行为与预期行为对齐的变换序列；
- 优点：不依赖完整模型，也不局限于神经网络内部分析；
- 典型解释对象：约束、随机性、状态特征、动作前提。

## 七、一句话总结

这篇论文最有启发性的地方在于：它把强化学习中的“解释”重新定义为一个**寻找认知差异来源的模型修正问题**，从而让解释更贴近人类真正关心的“为什么它和我想的不一样”。

## 八、算法如何实现（理论实现）

### 1. 输入与输出

如果从理论实现角度看，RLPE 框架的输入包括：

- actor 当前的实际策略；
- observer 期待的策略或动作偏好；
- 一个部分已知的 MDP/Markov game 模型；
- 一组可用的 model transforms。

输出则是：

- 一个能缩小预期差的 transform 序列；
- 由该序列导出的解释。

### 2. 核心思想怎么落成算法

这篇论文的本质是一个**搜索问题**。  
系统要做的不是直接读神经网络参数，而是反复问：

- 如果把模型改成这样，智能体会不会更像观察者预期的那样行动？

如果答案是“会”，那么这个修改就是解释候选。

### 3. 主流程

理论上可以写成以下过程：

1. 给定原始环境模型 `M`；
2. 计算 actor 在 `M` 上的真实策略；
3. 取 observer 的预期策略作为目标；
4. 遍历或搜索 transform 库中的候选变换；
5. 对每个变换后的模型 `T(M)`，重新求 actor 在该模型中的策略；
6. 比较该策略和 observer 预期是否更接近；
7. 若更接近，则把该变换记为有效解释候选；
8. 选出代价最小、语义最清晰、对齐效果最好的变换序列；
9. 输出解释。

### 4. 策略对齐如何理解

这篇论文的关键不在于“模型变了多少”，而在于：

- 变换后的策略是否更接近 observer 的预期。

所以核心评价量通常可以理解为某种**策略距离**或**行为一致性指标**。  
只要这个距离明显缩小，就说明该 transform 抓住了人和 agent 之间的认知差异。

### 5. 一个简化伪代码

```text
输入：原模型 M，actor 策略 pi_actor，observer 预期 pi_obs，变换集合 T
1. best_explanation = None
2. best_score = +inf
3. for 每个候选变换序列 seq in Search(T):
4.     M_seq = Apply(seq, M)
5.     计算 actor 在 M_seq 上的策略 pi_seq
6.     score = Distance(pi_seq, pi_obs)
7.     if score 更小:
8.         更新 best_score 与 best_explanation
9. 输出 best_explanation
```

## 九、算法如何实现（工程实现）

### 1. 工程模块如何拆分

如果真把这篇论文做成程序，模块可以拆成：

- `model_adapter`：读入或构造部分 MDP 模型；
- `transform_library`：管理所有可用变换；
- `policy_solver`：在变换后模型上重新求策略；
- `gap_evaluator`：比较 actor 策略与 observer 预期策略；
- `search_engine`：搜索最优 transform 序列；
- `explanation_renderer`：把 transform 序列转成文字说明。

### 2. 哪一步最耗时

最耗时的通常不是解释文本生成，而是：

- 枚举或搜索变换；
- 对每个变换后的模型重新求策略。

因此工程实现中，搜索效率是核心问题之一。

### 3. 怎样降低搜索开销

常见做法可以包括：

- 先按语义把 transforms 分组；
- 先测单步变换，再考虑多步组合；
- 对明显无效的变换提前剪枝；
- 缓存已经求过策略的变换模型；
- 使用近似策略评估，而不是每次都完整重训。

这类优化非常重要，否则系统会很慢。

### 4. 解释输出怎么做

从工程角度看，输出最好是结构化再转文本。  
也就是先得到：

- 变换类型：移除燃油约束；
- 行为变化：策略从“先加油”变成“先接客”；
- 差异原因：观察者忽略了资源约束。

再生成自然语言解释。这样比端到端自由生成更稳定。

### 5. 真正落地时的难点

这篇论文的工程难点主要包括：

- **observer 预期策略怎么表示**；
- **transform 库如何设计得既通用又有语义**；
- **每次变换后是否需要重新训练或重新规划**；
- **多智能体场景下 transform 的组合空间更大**。

所以在真实系统里，这个框架最适合用于：

- 模型结构相对清晰；
- 变换集合可控；
- 人类预期可以被显式表示的任务。
