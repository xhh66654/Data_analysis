# 十维动作 · 单树适配说明（不改 decision_tree 代码）

本文说明：在 **动作有 10 个维度、每步约有 1～3 维发生改变** 的前提下，若仍采用 **「多维结果看成一个动作 → 只建一棵决策树」** 的思路，如何与 **当前** `causal/decision_tree` 流水线对接。

**前提：** 不修改 `decision_tree` / `step_explain` 源码；适配工作主要在 **轨迹导出与动作编码表** 完成。

**推荐落地决策方案（轨迹出现过的模式 + 战术库合并）：** [十维动作-轨迹模式与战术库决策方案.md](./十维动作-轨迹模式与战术库决策方案.md)

---

## 1. 当前代码实际在做什么

| 项目 | 现状 |
|------|------|
| CSV 动作列 | 仅 **`action` 一列**（整数，如 0～3 表示四种机动） |
| 状态 | `s_0 … s_7` |
| FQE | `QHatNetwork` 输出 `(batch, n_actions)`，**每个时间步对全部离散动作类算一遍 Q** |
| l_hat | `q_all` 全长为 `n_actions`；`a_star = argmax`；`margin = top1 - top2` |
| VIPER | **一棵树**，标签 `y = action`（或 oracle 的 `a_star`） |
| 规则 | `IF … THEN 单一动作名/编号` |

**没有** `a_0…a_9`、**没有**「本步哪些维变了」的列、**没有** 按维跳过计算的逻辑。

因此：「十维单树」= 在进 CSV 之前，把 **10 维联合决策** 编成 **一个 `action` id**，其余流程与现网一致。

---

## 2. 两种总方案（决策只分两种）

```text
方案 A：10 维 → 10 棵树（每维一棵 CART）     → 需要改代码，本文不展开
方案 B：10 维 → 压成一个 action id → 1 棵树   → 本文主题，基本不改代码
```

| 对比 | 方案 B（单树 + 组合 id） | 方案 A（10 棵树） |
|------|-------------------------|-------------------|
| 改 `decision_tree` | **基本不改** | 需改 pipeline / viper 等 |
| CSV | 仍单列 `action` | 需 `a_0…a_9`（及可选 `chg_i`） |
| 规则 | 一个 THEN = 一种「模式/战术」 | 每维一条 THEN，更易读每一维 |
| FQE 每步计算量 | 对 **N 个组合类** 全算 Q | 可按维/按改动掩码优化（需改代码） |
| 适合 | 业务模式种类 **有限**（几十～几百） | 强调每维语义、维间组合要分开学 |

## 3. 方案 B：编码设计（数据侧）

### 3.1 流水线只认什么

```text
每行：s_0…s_7, s_next_0…s_next_7, action, reward, episode, dw, truncated
```

`action` 必须是 **非负整数**；`n_actions = max(action) + 1`（由 `run_pipeline` / FQE 自动推断）。

**建议 id 连续：** `0, 1, …, N-1`，避免中间缺号导致 Q 网络输出维度过大、部分类无样本。

### 3.2 一步决策要先定死的语义

1. **每个动作维**在本步的取值含义（如 `0=不变, 1=增, 2=减`，或档位枚举）。
2. **每步恰好 1～3 维发生有效变化**（在编码表里约束，无效组合不要写入 CSV）。
3. **训练与推理共用同一张编码表**（mode_id ↔ 10 维向量）。

### 3.3 编码方式选型

**推荐：业务模式表（最贴现代码）**

仿真/业务已定义有限种「本步机动」：

```text
mode_id  |  a_0  a_1  …  a_9  |  说明（中文名）
---------+---------------------+------------------
0        |  0   0   …  1      |  模式甲
1        |  0   2   …  0      |  模式乙
…        |  …                  |  …
```

- 导出 CSV 时：`action = mode_id`。
- **N 建议：** 几十～几百；每类样本尽量 ≥ 数千行（参考现 4 类机动 + 50 万行轨迹）。

**不推荐（除非 N 已人工截断）：纯数学组合**

- 仅「哪 1～3 维动」：C(10,1)+C(10,2)+C(10,3) = **175** 种 mask。
- 每维再多档位时，组合数可达 **上万**，多数类样本极少，树与 Q 都难学。

### 3.4 与「没变的维」的关系

- 未改变的维 **不会** 在流水线里单独出现。
- 它们被 **包进** 某个 `mode_id` 的固定向量里（通常未改维在表里为 `0=不变`）。
- FQE 仍对该行的 **所有 N 个 mode_id** 各算一个 Q 值，**不会** 跳过「本步未涉及的维」。

## 4. 现有各阶段如何自动适配（零代码）

| 阶段 | 行为（与现 4 类相同，仅 N 变大） |
|------|----------------------------------|
| `trajectory_io` | 读 `action` 列，`build_transitions` |
| FQE | `Q(s,·)` 维度 = N；训练 TD 用 **本行真实** `action` |
| `l_hat.csv` | `Q_hat_a0 … Q_hat_a{N-1}`；`a_star`、`margin` 在 **N 个组合** 上算 |
| `weights` | `margin` / `advantage` 加权 bootstrap |
| VIPER | 1 棵树；`pipeline_mode=rules` 时全表建树 |
| `rules.txt` / PDF | `IF … THEN <模式名或 id>`；叶节点类别分布为 **N 类模式** 的百分比 |
| `step_explain` | 在 **N 个组合** 上比 Q（需自备 N 个动作中文标签表，与 id 对齐） |

### 4.1 RUN_CONFIG

仍只需设置例如：

```python
"trajectory_csv": r"...\trajectory_xxx.csv",
"pipeline_mode": "rules",
"oracle_relabel": True,   # 树标签 = argmax Q，非原始 mode_id
"cart_class_weight": "balanced",
```

**不必** 也 **无法** 设置 `action_dim=10`（当前无此配置项）。

### 4.2 动作中文名（规则 / PDF）

`viper_cart` 通过 `DT/dt_auto_pipeline.CLASS_MAPPING` 显示类名（默认 0～9 为爬升、斜切等 **旧机动名**）。

- **不改代码时：** 新 id 可能显示为数字或错误映射；应用 **外部对照表** 解读 `rules.txt`。
- **若允许只改 DT 映射文件：** 将 `CLASS_MAPPING` 扩成 `0…N-1` → 你们的模式中文名（不改流水线逻辑）。

## 5. 导出侧检查清单

- [ ] 每个 `action` id 在轨迹中有 **足够行数**（稀少模式合并或删 id）。
- [ ] id **从 0 连续** 到 N-1（或明确接受稀疏 id 带来的空 Q 头）。
- [ ] 每行满足 **1～3 维变化**（在编码表定义，无效行勿导出）。
- [ ] 训练/回放/报告 **共用** 同一张 `MODE_TABLE`。
- [ ] 备一份 **`action_id → (a_0,…,a_9)`** 文档给人看规则与 PDF。

## 6. 运行步骤（最小）

```text
1. 定 MODE_TABLE：mode_id → (a_0,…,a_9)，名称与 1～3 维约束
2. 仿真/导出脚本写 CSV：action = mode_id（单列，列名仍为 action）
3. 修改 run_pipeline.py 中 trajectory_csv 指向新文件
4. python causal/decision_tree/run_pipeline.py
5. 查看 fqe_out/viper_out/rules.txt、policy_tree.pdf，用对照表翻译 THEN
```

产物路径与现网相同：`fqe_out/q_hat.pt`、`l_hat.csv`、`weights.csv`、`viper_out/rules.txt`、`data_flow_report.json`。

## 7. 预期现象与限制

### 7.1 计算行为

- **是：** 每个时间步对 **全部 N 个组合动作** 计算 Q（与现网对 4 类全算相同）。
- **不是：** 10 维各自算不算；未改维 **不会** 在代码里单独跳过。

### 7.2 规则与树图

- 叶节点可能出现 **两种模式占比接近**（如 49.6% / 50.0%），`class` 仍显示其中一个模式（argmax）。
- 含义是 **两种组合模式都常见**，不是「两个机动维各 50%」——除非模式表本身这样定义。

### 7.3 oracle

`oracle_relabel=True` 时，树拟合的是 **Q 最优组合** `a_star`，不一定等于仿真里记录的 `action`（探索/噪声时会有差异）。

### 7.4 何时单树不够用

- N > 几百且大量 id 样本 < 100；
- 需要汇报 **每一维** 的 IF-THEN；
- 需要 **只对改动的 1～3 维** 算 Q 以省算力。

上述情况应改 **方案 A（10 棵树）** 并修改 `decision_tree` 代码，而不是继续增大组合 N。

---

## 8. 与「49.6% / 50.0% 叶节点」的关系

单树 + 组合 id 时，叶子上是 **两种 mode_id 占比接近**，展示逻辑与现网相同（类别分布为真实标签百分比，仅叶节点显示 `class`）。

缓解方式（仍可不改 decision_tree 代码）：

- 合并相似 **mode_id** 再导出，减少相近模式抢样本；
- 增大 `cart_min_samples_leaf`，减少极小叶子；
- 弱模式在 MODE_TABLE 层做业务解释，不单信 argmax 的 `class`。

## 11. 一句话总结

**十维 + 单树 + 不改代码** = 在轨迹里 **仍只保留一列 `action`**，用 **模式表** 把「本步 10 维（1～3 维有变化）」编成 **0…N-1**；现有 FQE → VIPER → 规则流程 **原样运行**，人用 **id↔10 维对照表** 读懂 `rules.txt` 与 PDF。
